Protocol. Query timing is single-thread, one query at a time, k=10, one warm-up pass, three timed repeats, median reported. Queries 0–4999 are the tune half and 5000–9999 the eval half; every reported number comes from the eval half.

2Exact Baseline and the Recall Metric (Part 1)

2.1recall@10, and why ties matter

A returned id counts as correct when its exact distance is ≤ the exact distance of the true 10th neighbour, not when it appears in a stored top-10 id list. If the 10th and 11th neighbours are equidistant, returning either is equally right.

This is not pedantry. SIFT vectors are integer-valued, so exact ties are common — 1.37% of queries have a tie at d10 == d11 and 12.03% have one somewhere in the top 11 (GloVe: 0.01%). A naive id-overlap metric scores the dataset's own published neighbours at 0.99935 rather than 1.0, putting a floor under SIFT recall that no index could cross. The metric also recomputes the exact distance of every returned id from the base vectors instead of trusting what the index reports — that matters for IVF-PQ, whose distances are estimates: on a test index, believing them gave 0.76 recall where the truth was 0.37. Twelve unit tests cover the metric, including the rank-10 tie, duplicate ids, −1 padding, and agreement with an independent naive implementation on tie-free data.

2.2One query at a time versus one batch

SIFT: {s_exact:.2f} qps one-at-a-time against {s_batch:.1f} qps batched, both single-threaded — a {s_sp}× gap. GloVe: {g_exact:.2f} → {g_batch:.1f} qps ({g_sp}×). Holding the thread count fixed is the point: comparing one-at-a-time against a multi-threaded batch would confound batching with parallelism, and the explanation below would be partly wrong.

Both modes do identical arithmetic. One query at a time is a matrix–vector product: all 488 MB of base vectors stream from RAM, each used for a single multiply-accumulate, then evicted — the kernel is bound by memory bandwidth, not by the CPU. Batched, it becomes a matrix–matrix product handed to BLAS: a tile of base vectors is loaded into L2/L3 once and reused against all 5,000 queries, so each byte fetched from RAM does thousands of times more arithmetic. That converts a bandwidth-bound kernel into a compute-bound one which can saturate the SIMD units. Per-call overhead is amortised too, but cache reuse dominates — §4 corroborates this: at 100K the base is 51 MB and partly L3-resident, and exact search runs 24% faster than the n−1 line predicts.

3.1Why IVF-PQ never reaches 0.95

IVF-PQ is the one index that fails, on both datasets, at every code size: peak recall {s_pq:.3f} on SIFT (m=64, 74 B/vector) and {g_pq:.3f} on GloVe (m=50, 59 B/vector). Recall rises monotonically with code size — SIFT 0.416 / 0.595 / 0.745 / 0.886 for m = 8/16/32/64 — but plateaus below target.

The mechanism is measured, not asserted

On GloVe the median PQ reconstruction error ‖x − decode(encode(x))‖ is 0.0712, while the median rank-10 margin d11 − d10 that PQ must resolve to get the top-10 boundary right is 0.00185 — a factor of 38. Any distance computed against a reconstruction is uncertain by far more than the gap being judged, so ordering at the boundary is dominated by quantisation noise. This is a ceiling, not a tuning problem: more nprobe widens the candidate set but the ranking inside it stays wrong, which is exactly what the flat tails in Figures 2–3 show.

4Scaling: the Cost of Recall 0.95 versus n (Part 3)

Hypotheses were committed to git before this ran; all six held. Fitted throughput exponents: exact n{e_exact:+.3f}, IVF-Flat n{e_ivf:+.3f}, HNSW n{e_hnsw:+.3f} — strictly ordered, as H3.3 predicted. Exact search pays linearly because it reads every vector; HNSW barely notices because greedy descent visits O(log n) nodes, and the exponent falls short of 0 only because efSearch must itself grow with n to hold recall fixed. Two consequences follow. First, HNSW's advantage over IVF-Flat grows with scale: 1.63× at 100K, 2.58× at 300K, 2.91× at 1M — a graph's logarithmic advantage needs scale to pay for itself. Second, build cost moves the other way: HNSW costs 134.6 µs/vector at 100K and 220.3 µs/vector at 1M, 1.64× more per vector, super-linear as O(n log n) implies, while exact search's "build" is a memcpy. The one deviation I predicted also appeared: exact at 100K hit 286.9 qps against a 231 qps extrapolation — 24% above the line — which is the L3 cache effect named in the hypothesis as the first thing to check.

5Hard Geometry: Making Both Indexes Fail (Part 4)

A 2×4 design varying one thing: distance concentration. Uniform coordinates in [0,1]d make every pairwise distance converge as d grows; the clustered control has the same n, the same d, the same generator and the same search budget, and differs only in geometry. Since a distance costs O(d), reporting throughput alone would measure arithmetic and call it geometry — so the primary measurements are dimension-independent: recall at a fixed budget (efSearch=64, nprobe=16 everywhere) and the fraction of the data actually scanned, read from FAISS's own distance counters. Relative contrast RC@10 across d = 16/64/256/1024 falls {rc_u} for uniform data while the control holds {rc_c} — SIFT measures 2.63 and GloVe 1.51, so the sweep spans from easier than SIFT to far harder than GloVe.

H4.5 deserves a caveat I would rather state than hide

I predicted HNSW would degrade at least as fast as IVF-Flat, and the pre-registered criterion — absolute recall drop across the uniform row — says it did: 0.867 against 0.749. But HNSW starts higher and ends higher (0.127 vs 0.078) while scanning three times less data (0.97% vs 2.92%). Normalised for work, HNSW is clearly the better index at d=1024, the opposite of what "degrades faster" suggests. The criterion was poorly chosen; the verdict is reported as the pre-registration demands, and should be read with this.

6Answers (Part 5)

Q1 — At recall 0.95, which index is fastest on each dataset, and does the answer change between datasets?

HNSW on both, but the margin and the settings change. SIFT: {s_hnsw:.0f} qps (M=16) against IVF-Flat's {s_ivf:.0f} (nlist=4096) — {s_hi}×, and {s_he}× the exact baseline. GloVe: {g_hnsw:.0f} qps (M=32) against {g_ivf:.0f} (nlist=16384) — only {g_hi}×, and {g_he}× exact. The winner is stable; the margin halves and the best build setting flips in both families. On GloVe HNSW needs M=32, and M=8 cannot reach 0.95 at all (peak 0.865), while IVF-Flat's optimum moves from 4,096 to 16,384 cells. The cause is geometry: GloVe's RC@10 is 1.51 against SIFT's 2.63, so the graph has a weaker distance gradient to descend and needs more degree and more candidates. Absolute throughput falls ~10× for HNSW between the datasets but only ~5× for IVF-Flat — the harder geometry costs the graph more than it costs the partition.

Q2 — What do the indexes cost in build time and memory? What does PQ save, and what does it give up?

See Table 2. On SIFT, HNSW costs 208 s and 656 B/vector — 512 of data plus 144 of graph; IVF-Flat 62 s and 522 B/vector, nearly free on top of the raw vectors since it stores only ids and cell assignments. GloVe is dearer for HNSW (434 s, 672 B/vector) because higher degree is needed to reach the target at all. PQ saves an order of magnitude: 74 B/vector on SIFT, 7× smaller than flat, and 59 on GloVe, built in ~70 s. What it gives up is the top of the recall range outright — it cannot reach 0.95 on either dataset at any code size tested, for the quantisation-versus-margin reason in §3.1. PQ is the right choice only when the memory budget is binding and ≈0.88 recall is acceptable.

Q3 — What did Parts 3 and 4 show, and what do they imply about when the headline numbers could mislead?

Part 3: the cost of recall 0.95 scales as n{e_exact:+.2f} / n{e_ivf:+.2f} / n{e_hnsw:+.2f} for exact / IVF-Flat / HNSW, so the ranking itself is a function of scale — at 100K HNSW and IVF-Flat are within 1.63×, at 1M they are 2.91× apart. Part 4: at a fixed budget, recall collapses from 0.994 to 0.127 as contrast vanishes, while a control at the same dimension holds 0.904. Together they say a headline ANN number is a property of this dataset at this size, not of the index. The same HNSW configuration delivers 5,817 qps at recall 0.95 on SIFT, 584 on GloVe, and cannot reach 0.95 at all on uniform d=1024. Quoting one number without the dataset's size and contrast is close to meaningless.

Q4 — With 150,000 vectors, or 10 million, a 100 ms budget and 16 GB of RAM — would you use ANN, and with what settings?

At 150K, no. Extrapolating the measured exact-search fit gives ≈190 qps, i.e. ≈5 ms per query — twenty times inside the budget — for 77 MB of RAM, exact answers, no build step and no parameters to mis-set. ANN would still be ~30× faster (at 100K we measured HNSW at 8,858 qps against exact's 287), so reach for it if throughput rather than latency is the constraint; otherwise the complexity buys nothing the budget needs.

At 10M, yes, necessarily. Exact extrapolates to ≈1.9 qps, ≈530 ms per query — over budget by 5×. HNSW extrapolates to ≈2,000 qps (0.5 ms) at ≈6.6 GB; IVF-Flat to ≈390 qps (2.6 ms) at ≈5.2 GB. Both fit 16 GB. I would default to IVF-Flat with nlist ≈ 32,768 — continuing the observed 1,024 → 4,096 → 8,192 trend — and nprobe tuned on held-out queries: it meets the budget with 40× headroom, costs about half the build time, and is far easier to update incrementally. Choose HNSW M=16 instead if per-query latency is the binding constraint. PQ only if you must fit under ≈1 GB, accepting recall ≈0.89. Caveat: these extrapolate a decade beyond the measured range from three points each; I would re-measure at 10M before committing.

Q5 — Name two ways your own benchmark could be misleading, and say whether you tested them.

(a) One shared cloud VM. Every number comes from a single 4-core Kaggle instance. I did test the noise — spread across repeats was 1.8–3.1%, recorded per row as qps_spread_pct, and machine_id is identical across all {rows} rows, so no comparison spans hardware. I did not test whether the ranking survives a different microarchitecture, or more cores: all query timing is deliberately single-thread, and HNSW and IVF parallelise differently, so a multi-core ranking could differ.

(b) Choosing the best build setting on the evaluation split. Part 2's per-index envelope picks the best of 3–4 build settings using eval recall, which is mild selection bias. I tested this only partially: Part 3 avoids it entirely by selecting the search parameter on the tune half and reporting eval timings, and the bias is bounded — a 5,000-query recall mean has a standard error near 0.0014, far below the gaps involved (SIFT HNSW M=16 at 5,817 qps against M=32 at 5,505).

(c) A third risk I did not fully resolve. Part 2 interpolates throughput to recall 0.95, while Part 3 reports the cheapest measured grid point reaching it, which overshoots — HNSW at 1M is 5,817 qps interpolated against 4,237 qps measured at recall 0.9712. These are different quantities and are never mixed within a table, but a reader comparing across sections could be misled.

7Reproducing This

bash run_all.sh in code/ regenerates every number, figure and table from the data files; --quick does the same on 100,000 SIFT vectors in under two minutes. Neither needs a GPU — ground truth falls back to FAISS on the CPU — nor a Hugging Face token. results/results.csv carries all {rows} runs with their parameters, recall, median QPS and spread, latency, build time, memory, thread count, query split and machine. The Part 3 and 4 hypotheses were committed to git before those experiments ran, and the recall metric's twelve unit tests are the pipeline's first stage, so a broken metric stops the run before it produces numbers.

Data and tools. Datasets: SIFT-128-euclidean and GloVe-100-angular from ann-benchmarks.com — data only, as the ground rules require. Indexes: FAISS {faiss} (Johnson, Douze & Jégou, IEEE Big Data 2019); HNSW (Malkov & Yashunin, TPAMI 2018); product quantization (Jégou, Douze & Schmid, TPAMI 2011).
